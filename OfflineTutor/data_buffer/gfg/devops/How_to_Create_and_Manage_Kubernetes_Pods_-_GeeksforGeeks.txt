# How to Create and Manage Kubernetes Pods - GeeksforGeeks

A Pod represents a single instance of a running process in your cluster and can contain one or more containers. Think of a Pod as a lightweight, application-specific "logical host". All containers within a single Pod are guaranteed to be co-located on the same worker node, and they share the same environment. This shared context is the magic of the Pod abstraction and includes:   Shared Networking: Every Pod is assigned a unique IP address. All containers within that Pod share this IP address and port space, meaning they can communicate with each other using localhost.   Shared Storage: Containers within a Pod can share storage volumes, allowing them to have a common filesystem and exchange data seamlessly. In the following diagram, you can see pods that contains one or more containers. The cylinder-like structures represent volumes, which are used to store data for containers. The large circles represent pods, which are the smallest deployable units in Kubernetes.A Pod can contain one or more containers, and all containers inside a Pod share:The same IP addressStorage volumesNetwork resourcesOther required configurationsPods allow easy movement of containers within a cluster. They are created and managed by controllers, which handle:Rollouts (new versions of Pods)Replication (keeping the right number of Pods running)Health monitoring (restarting or replacing failed Pods)If a node fails in the cluster, the controller detects the unresponsive Pod and replicates it on another node to continue the same function.The three commonly used controllers are:Jobs: For batch tasks that run once and complete (ephemeral).Deployments: For stateless and persistent applications, such as web services.StatefulSets: For stateful and persistent applications, like databasesPod YAML StructureA Kubernetes Pod can be defined using a YAML manifest. The manifest describes the desired configuration of the Pod.A basic Pod YAML file looks like this:
            YAML

    apiVersion: v1
kind: Pod
metadata:
  name: nginx
  labels:
    app: nginx
spec:
  containers:
    - name: nginx
      image: nginx:latest
      ports:
        - containerPort: 80

The main fields in a Pod manifest are:apiVersion: Specifies the Kubernetes API version used by the object.kind: Specifies the type of Kubernetes object. For a Pod, it is Pod.metadata: Contains information such as the Pod name and labels.spec: Defines the desired configuration of the Pod.containers: Specifies the containers that should run inside the Pod.image: Specifies the container image to use.ports: Specifies the container ports used by the application.The spec section is where most of the Pod configuration is defined.The Pod LifecycleA Pod follows a defined lifecycle and exists in one of several high-level phases.   1. PendingThe Pod has been accepted by Kubernetes, but it is not running yet.This phase can occur when:The Pod is waiting for the scheduler to assign a node.Container images are being downloaded.Required resources are not currently available.The Pod is waiting for storage or other dependencies.A Pod can remain in the Pending phase until all required conditions are satisfied.2. RunningThe Pod has been assigned to a node and its containers have been created.A Pod is in the Running phase when:It has been scheduled to a node.Its containers have been created.At least one container is running.A container may also be starting or restarting.The Running phase does not necessarily mean that every container is ready to receive traffic.3. SucceededThe Pod has completed its task successfully.This happens when:All containers have terminated.All containers exited successfully with status 0.Kubernetes does not restart the containers.Succeeded is commonly seen with Pods created by Jobs.For example, a Pod running a backup or batch-processing task can enter the Succeeded phase after completing its work.4. FailedThe Pod has finished running, but the task was not successful.This happens when:All containers have terminated.At least one container terminated with a non-zero exit status.The Pod cannot complete its intended task successfully.A Failed Pod may contain useful information in its logs and events for troubleshooting.5. UnknownThe Unknown phase means Kubernetes cannot determine the current state of the Pod.This can happen because:The control plane cannot communicate with the node.There is a network communication problem.The node becomes unreachable.The kubelet on the node stops responding.Kubernetes may continue trying to determine the actual state of the Pod.Pod LifecyclePod Restart PolicyThe restartPolicy field defines what Kubernetes should do when a container inside a Pod terminates.The available restart policies are:Always: Kubernetes always restarts the container when it terminates. This is the default policy.OnFailure: The container is restarted only when it terminates with an error.Never: Kubernetes does not restart the container after it terminates.Example:spec:  restartPolicy: NeverRestart policies are especially important for Pods that run short-lived tasks.For example, a Kubernetes Job commonly uses:restartPolicy: NeverPod SchedulingWhen a Pod is created, the Kubernetes scheduler determines which worker node should run it.The scheduler considers factors such as:Available CPU and memory.Resource requests.Node constraints.Node affinity and anti-affinity.Taints and tolerations.Other scheduling rules.By default, Kubernetes automatically selects a suitable node.You can also influence Pod placement using scheduling features such as:nodeSelector: Runs a Pod on nodes with matching labels.Node Affinity: Provides more flexible rules for selecting nodes.Taints and Tolerations: Control which Pods can run on particular nodes.Working with Kubernetes PodsPod Operating SystemThe operating system (OS) running inside pods is typically determined by the container image used to create the pod's containers. Pods in Kubernetes can run containers based on various Linux distributions, such as Ubuntu, Alpine Linux, or CentOS, among others.Pods and ControllersPods are usually not created directly for long-running applications. Kubernetes controllers manage Pods and help maintain the desired state of an application.The common relationship is: Different controllers are used for different workloads:Deployment: Manages stateless applications and supports scaling, rolling updates, and rollbacks.StatefulSet: Manages stateful applications that require stable identities and storage.DaemonSet: Ensures that a Pod runs on each selected node.Job: Runs a task until it successfully completes.CronJob: Creates Jobs on a scheduled basis.For example, when a Pod managed by a Deployment fails, the Deployment and its ReplicaSet work together to create a replacement Pod. For most application workloads, using a controller such as a Deployment is preferred over creating Pods directly.Getting Started with Kubernetes PodLet's create and work with a Kubernetes Pod using both imperative and declarative approaches.Step 1: Create a Pod ImperativelyFor a quick test, create an Nginx Pod using a single command:kubectl run nginx --image=nginxThis creates a Pod named nginx using the Nginx container image.Check whether the Pod is running:kubectl get pods Step 2: Generate a Pod YAML ManifestYou can generate the YAML configuration of the Pod without creating it in the cluster:kubectl run nginx --image=nginx --dry-run=client -o yaml > pod.yamlThe --dry-run=client option prevents Kubernetes from creating the Pod, while -o yaml prints the resource definition in YAML format.The generated pod.yaml contains fields similar to:apiVersion: v1kind: Podmetadata:  name: nginxspec:  containers:    - Two common patterns are Init Containers and Sidecar Containers.Init ContainersAn Init Container is a specialized container that runs and completes before the main application containers are started. They are defined in a separate initContainers block in the Pod manifest. You can have multiple Init Containers, and they will run sequentially. Each one must exit successfully before the next one is started.   Use cases for Init Containers:Waiting for a backend service like a database to become available.Running a setup script to prepare a database schema or pre-load data.Cloning a Git repository into a shared volume for the main application to use.Registering the Pod with a central directory before the main application starts.Sidecar ContainersA Sidecar container runs alongside your main application container within the same Pod. Unlike an Init Container, it starts with and continues to run for the full life of the application container. This pattern allows you to extend or enhance the functionality of the main container without adding complexity to the application's own codebase.   Use cases for Sidecar Containers:A sidecar can tail log files from a shared volume and forward them to a centralized logging system.   A sidecar can collect metrics from the main application and expose them to a monitoring system like Prometheus.In a service mesh like Istio, a sidecar proxy handles all inbound and outbound network traffic for the main container, enabling features like traffic management, security, and observability.A sidecar can sync files from a central source (like an S3 bucket or a Git repository) into a shared volume for the main application to consume.Communication between podsIntra-Pod (Same Pod): Containers within the same Pod share a network namespace and a single IP address. They communicate with each other via localhost using different port numbers.Inter-Pod (Same Node): Pods on the same worker node communicate through a virtual bridge (like cbr0). Each Pod has a unique private IP, allowing them to send packets directly to one another without NAT.Inter-Pod (Different Nodes): Communication across nodes is managed by a CNI plugin (like Calico or Flannel). It creates an "overlay network" that routes traffic from one node to the IP of a Pod on another node.Service-Level Discovery: Since Pod IPs are temporary, a Service provides a stable "Virtual IP." Other Pods talk to the Service, which then load-balances the traffic to the correct backend Pods.External Access: To reach Pods from outside the cluster, you use an Ingress or a LoadBalancer service, which maps external traffic to the internal Pod network.Kubernetes Pod Updates and ReplacementPods are designed to be replaceable and are generally treated as ephemeral resources. For application updates, Kubernetes controllers such as Deployments create new Pods and remove old Pods according to the configured update strategy.If a standalone Pod fails, Kubernetes does not automatically recreate that Pod unless it is managed by an appropriate controller. Controllers such as Deployments, ReplicaSets, StatefulSets, DaemonSets, and Jobs are responsible for managing Pods according to their workload requirements.Basic Kubectl Commands for Kubernetes PodsCreate Pod: A pod can be created by using the create command format.kubectl create -f [FILENAME]In the [FILENAME], you need to insert the required filename with which you want to create your file, and then a new pod with the name GeeksforGeeks will be created.To Delete Kubernetes Pod:  Delete the pod using the below command.,kubectl delete -f FILENAME Here the pod named GeeksforGeeks will be deletedTo Get Kubernetes  Pod: To see the number of pods available in the particular namespace can be seen using the below command.kubectl get pod <name> --namespaceTroubleshooting ProblemCommandList Podskubectl get podsShow Pod detailskubectl describe pod <pod-name>View logskubectl logs <pod-name>View previous container logskubectl logs <pod-name> --previousOpen a shell inside a containerkubectl exec -it <pod-name> -- shView Pod IP and nodekubectl get pod -o wideView Pod eventskubectl describe pod <pod-name>Check all Podskubectl get pods -AIf a Pod is stuck in Pending, use kubectl describe pod to check scheduling events.
